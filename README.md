# 中开服务官网 · 内容中台产品化项目

> 把「改一个字要等外包两周」的官网，做成运营自己能在 5 分钟内发布的内容产品。
> 本仓库是这套系统的**产品经理交付物全集**：调研 → 设计思路 → PRD → 信息架构 → 内容模型 → 交互原型 → 性能复盘 → 验收用例 → 迭代路线。

- 产品代号：ZK-CMS（中开内容中台）
- 角色：0→1 独立交付（产品 + 前端 + 后台 + 部署）
- 周期：2026.09 立项 → 2026.10.15 首次提交 → 至今持续迭代
- 线上：`https://demo.zhongkaisk.cn/`（官网与后台同端口 6993）
- 规模：41 个静态页 / 218 个可编辑字段 / 15 款产品 / 7 个交付基地 / 35 个后台接口

**在线看**：[项目落地页](https://zhouzhou1699.github.io/zhongkai-cms-prd/) · [可点原型](https://zhouzhou1699.github.io/zhongkai-cms-prd/prototype/)

## 一、这个项目解决什么问题

不是「不好看」，是**改不动**。

原官网由外包制作，任何一处文案修改都要走「提需求 → 报价 → 排期」，一次小改版两周起步。产品线从 5 条扩到 15 条、基地从 1 个扩到 7 个之后，官网与业务节奏彻底脱节：销售在客户面前讲的产品，官网上还没有。

所以本次立项的命题不是「重做视觉」，而是**重构内容的生产关系**：

| 维度 | 改造前 | 改造后 |
|---|---|---|
| 改一句话 | 提需求 → 排期，2 周起 | 运营在后台改，保存即生效 |
| 加一个产品 | 新增页面 + 改导航 + 改列表，开发介入 | 后台「新增产品」，自动进导航/产品超市/相关推荐 |
| 发布耗时 | 全量 6 个生成器串行子进程，4.5 s | 页级增量，全量 0.22 s，单页 0.07 s |
| 发布失败 | 站点半新半旧，无人知晓 | 失败自动回滚 41 页 + 内容，逐页报告 |
| 多人同时改 | 后保存的整份覆盖前者，先保存的白干 | 乐观锁 `rev` 比对，冲突 409 并给出字段级差异 |
| 上线方式 | 找技术打包上传 | 页面上点「发布到网站」，或 git push 自动部署 |

## 四、关键结论（先看这五条）

1. **不要换 CMS。** 「静态站 + 单一 JSON 真源 + 自制后台」这条路线本身是对的：零第三方依赖、可离线、成本极低。问题集中在「缺一层事务语义」和「缺预览与富文本」，不是选型错了。
2. **先修事务，再谈体验。** 内容丢失（多人覆盖）和「假回滚」是唯二会造成真实资产损失的问题，优先级高于所有视觉优化。
3. **官网唯一的转化入口当时是空的。** 全站 41 个页面只有一个 `<form>`，还是登录页；「提交需求」按钮点了什么都不发生，而页面写着「1 个工作日内联系您」。这是商业价值最高的一条待办。
4. **性能问题 87% 是进程启动成本。** 4.5 s 里有 3.9 s 在开 Python 进程，真正渲染一页只要 50–100 ms。改进程模型，比优化渲染代码收益大一个数量级。
5. **SEO 基建缺失是可量化的损失。** 有 sitemap 与 robots，但 `robots.txt` 里的 Sitemap 指向 `127.0.0.1:6993`（内网地址）；41 页零 OG 卡片、零 canonical、零 JSON-LD。

## 五、复现与校验

```bash
# 度量来自真实系统，可重跑（需在有 company/ 源码的环境）：
python scripts/collect_metrics.py      # 输出 data/metrics-code.json
python scripts/dump_content_model.py   # 输出 data/fields.json / pages.json
```

文档里的每个数字都能在 `data/` 里找到出处。这是刻意设计的：**产品文档不应该有无法追溯的数字。**
