# 迭代路线图

> 原则：**先修会丢东西的，再修丢面子的，最后修锦上添花的。**
> 每一版都有可验收的产出，不做「大版本一次性交付」。

## 三、明确不做（并记录理由，防止被反复提）

| 不做 | 理由 | 何时重新考虑 |
|---|---|---|
| 换 Headless CMS（Strapi/Directus） | 需 Node + 数据库常驻，生产环境是 CentOS 7 + Python 3.6 + 无外网 | 内容团队 > 5 人 / 需多语言 ≥3 / 需审批流 / 页面 > 200 |
| WYSIWYG 编辑器 | 引入 XSS 面与结构漂移，生成器是 f-string 拼接承受不了 | **不重新考虑**（用 Markdown 替代） |
| 前端框架重写（Vue/React） | 现有 2,416 行原生 JS 交互逻辑是对的，缺的是组件能力 | 后台页面数翻倍 / 需要复杂表格与拖拽 |
| 动态渲染（SSR） | 静态 HTML 首字节即内容，SEO 与速度都更优 | 需要个性化内容（登录态首页） |
| 支付 / 在线下单 | 需要支付资质与对账体系，客单价高走线下 | 出现标准化低价产品线 |
| 自研标注组件 | Label Studio 已覆盖 25 类标注类型，重写无差异化价值 | 出现 Label Studio 不支持的模态 |

## 四、版本节奏

```
v1.0 ──► v1.1 ──► v1.2 ──► v1.3 ──► v1.4
内容模型  事务层   体验性能  转化+SEO   埋点+CI
                    (当前)
```

- **两周一版**，每版必须有一个可演示的完整闭环。
- 每版上线前：跑 118 项自动化断言 + 20 项人工走查 + 41 页 md5 记录。
- 每版上线后：观察 3 天 `audit.log` 的发布成功率与冲突次数，异常则回滚。

## 五、如果要我重做一次，会改什么

1. **第一天就做 schema 单一真源**。字段元数据混在 content.json 里，导致后来每加一个字段要改三处，这是最大的返工来源。
2. **第一天就用对象数组而不是平行数组**。`feats` + `feats_names` 的位置对齐在半年里埋了两次 bug。
3. **第一版就做预览**。没有预览的那两周，运营把线上当预览环境，这不是体验问题，是事故源。
4. **先做表单再做设计**。「唯一转化入口是空的」这件事，比任何视觉问题都严重，但它不会自己喊出来——必须靠产品主动去查。
5. **所有「已回滚」「已备份」的提示，配一个能自证的脚本**。假回滚这件事，是文案先于实现写下的结果。
