# 发布性能复盘：4.5 s → 0.22 s

> 这份复盘的重点不是「我优化了多少」，而是**怎么在动手前先证明瓶颈在哪**。
> 全部数字可用 `scripts/bench_build.py` 复跑。

## 一、现象

运营的抱怨是「发布要等 4–5 秒，而且整个站都在重建」。技术侧的直觉反应是「渲染太慢，去优化模板拼接」。这个直觉是错的。

## 二、测量（先量，再改）

### 2.1 拆解一次全量发布

原实现：点发布 → 顺序 `subprocess` 跑 6 个生成器 → 每个生成器独立 Python 进程，各自 `import common` 重新读 content.json、重建注册表 → 写 HTML。

| 组成 | 实测 | 占比 |
|---|---|---|
| Python 进程启动 × 6 | 0.20 s × 6 ≈ 1.2 s | — |
| 每个进程 `import common`（含读 content.json + 建注册表 + 打补丁导航） | 0.27 s × 6 ≈ 1.6 s | — |
| 进程间 I/O、调度、退出 | ≈ 1.1 s | — |
| **真正渲染 41 页** | **47 ms/页 平均 ≈ 0.17 s** | **≈ 4%** |

**结论：4.5 s 里约 96% 是进程模型的成本，不到 4% 是渲染。**

这是一个典型的「优化错了地方」陷阱：如果按直觉去优化 f-string 拼接，最多只能省 0.17 s 里的一部分，用户根本感知不到。

### 2.2 改造后的实测

| 场景 | 改造前 | 改造后 | 提速 |
|---|---|---|---|
| 全量 40 目标（41 页 + 3 独立站） | 4.5 s | **0.22 s**（冷热基本一致） | **≈ 21×** |
| 单页 | 4.5 s（全量） | **0.073 s** | 62× |
| 单页渲染本身 | 47 ms | 4 ms（预热后） | 12× |
| 内容无变化时点发布 | 4.5 s | **0.27 s**（直接返回 mode=none） | 17× |
| 一次 Python 进程启动（对比基线） | 0.21 s | — | 单页 0.073 s **比启动一次 Python 还快** |

> 最后一行是这次改造最有说服力的指标：**改造后单页发布的耗时，小于「用旧方案启动一个进程」的耗时。**

## 三、改法：页级构建表 + 单进程

### 3.1 把「6 个脚本」变成「1 张表」

```python
SIMPLE_PAGES = {
    "index.html":       ("gen_home",            "build_service_home"),
    "group.html":       ("gen_home",            "build_group_home"),
    "products.html":    ("gen_service_pages",   "gen_products"),
    ...                                     # 16 个固定页
}
PSEUDO_PAGES = {
    "news-articles":    ("gen_group_pages",     "gen_news_details"),
    "product-sites":    ("gen_product_sites",   "main"),
}
```

6 个生成器仍在，但不再由 `subprocess` 各起一个进程，而是**在同一个进程里 import 一次、按需调用**。进程启动与 `import common` 的成本从「每页付一次」变成「整个发布付一次」。

### 3.2 模块缓存 + 原地刷新

```python
_MODS = {}
def _mod(name):
    if name not in _MODS:
        _MODS[name] = importlib.import_module(name)
    return _MODS[name]

def reload_content(content_path=None):
    common = _mod("common")
    data = common.load_content()
    common.CONTENT.clear(); common.CONTENT.update(data)      # 原地
    common.PRODUCTS[:] = common._load_products()             # 切片赋值！
    common.BASES[:]    = common._load_bases()
    common._patch_dynamic_nav()
```

**这里有个必须写下来的坑**：生成器都是 `from common import *`，拿到的是**对象的引用**。所以刷新派生数据时必须用切片赋值（`PRODUCTS[:] = ...`）原地改，不能重新绑定（`PRODUCTS = ...`）——否则生成器还看着旧清单，表现为「加了产品但页面里没有」。这个 bug 在开发时出现过一次，排查了很久。

### 3.3 页级增量：字段 → 页面影响面

只有「单进程」还不够：改一个产品简介仍然重建 41 页。所以加了第二层：算影响面。

```
diff(上次发布的基线, 当前内容) → 改动路径集合
   ↓ _targets_for(paths)
目标页集合（可能触发全量）
   ↓ build(targets)
只构建这些页
```

规则表见 [PRD §4.4](03-PRD-内容中台.md)。核心是三条「必须全量」的红线：`site.*`（页脚在每页）、`products[]`（导航在每页）、无基线（首次）。

### 3.4 基线不能乱推进（踩过的坑）

增量发布依赖「上次发布时的内容快照」作为基线。第一版实现里，只要发布流程跑完就推进基线——包括「内容无变化、跳过重建」的情况。

后果：**删除类改动永远生效不了**。因为「删掉首页资讯区的一条」这个操作，如果上一次发布因为无变化跳过了、却推进了基线，那么下次再算 diff 时，两边都是「已删除」状态，diff 为空，永远判「无变化」，首页残留内容再也重建不回来。

修法：注释写死在代码里——

```python
# 注意：这里不更新基线。基线只代表「页面真的建成什么样」，
# 一旦跳过重建就推进基线，会让清空/删除这类改动永远判成「无变化」，
# 首页/资讯页残留内容就再也重建不回来（线上踩过的坑）。
```

**这条是本项目最有价值的一条工程经验**：增量系统的正确性不取决于「算得准」，而取决于「基线的语义是否唯一」。基线只能代表「线上文件的真实状态」，不能代表「我处理过的内容」。

## 四、为什么不再往下优化

当前 0.22 s 已经远低于人的感知阈值（约 0.3–1 s 才算「等一下」）。继续优化的方向与收益：

| 方向 | 预估收益 | 为什么不做 |
|---|---|---|
| 渲染层换模板引擎 / 减少字符串拼接 | 0.17 s → 0.10 s | 收益 0.07 s，无人能感知，但引入依赖与重写风险 |
| 并发构建（多进程/多线程） | 0.2 s → 0.1 s | 进程启动成本会吃掉收益；且并发写同一目录增加失败模式 |
| 增量到「字段级局部替换」（不重渲整页） | 0.2 s → 0.05 s | 会把生成器变成「打补丁器」，模板与产物双向耦合，维护成本爆炸 |
| 发布异步化 + 前端进度（已在做） | 感知等待 → 0 | ✅ 已做，这是正确的方向：**降低感知延迟比降低真实延迟便宜** |

**判断原则**：优化到「用户感知不到等待」就停。继续优化的边际收益是零，但风险不是零。
