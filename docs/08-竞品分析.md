# 竞品与替代方案分析

> 目的不是「证明我选对了」，而是把**每条路线的失败模式**写清楚，让后来接手的人知道为什么不能随便换。

## 一、竞品官网（同业）

### 海天瑞声（688787）

| 维度 | 观察 | 评价 |

## 二、技术方案（三条路线对比）

| 维度 | A. 静态站 + JSON 真源 + 自制后台（**采用**） | B. Headless CMS（Strapi / Directus / Payload） | C. 传统 CMS（WordPress） |
|---|---|---|---|
| 运行时 | Python 标准库（无依赖） | Node + 数据库常驻 | PHP + MySQL |
| 部署 | 静态文件 + Nginx | 需要进程守护、备份数据库 | 需要 LAMP + 插件管理 |
| 离线可用 | ✅ | ❌ | ❌ |
| 首屏性能 | 静态 HTML，TTFB 即内容 | 需 SSG 层或 SSR | 动态渲染 |
| 内容模型 | 自定义（218 字段） | 强（可视化建模） | 弱（post/page 二元） |
| 权限 / 审批流 | 自建（2 角色） | 开箱 | 插件 |
| 版本 / 回滚 | 自建（60 快照 + 字段 diff） | 开箱 | 插件 |
| 升级维护 | 无依赖，不升级 | 每年大版本升级、依赖漏洞 | 插件漏洞频发 |
| 上手成本（新同事） | 需读 3,000 行 Python | 需学框架 | 需学主题/插件体系 |
| 适用规模 | ≤5 人内容团队、≤100 页 | 多团队、多语言、审批流 | 博客 / 小型站 |

### 为什么 A 在**我们的约束下**是最优

1. **环境约束**：生产是 CentOS 7 + Python 3.6 + Nginx 静态托管 + 无外网。B/C 直接出局（无法装依赖）。
2. **产物约束**：官网 SEO 与首屏敏感。静态 HTML 是最优解，B 路线要额外加一层 SSG 才有同等效果（= 两层系统）。
3. **团队约束**：无专职前端。A 的全栈是「Python 标准库 + 原生 JS」，任何人能读。
4. **失败模式约束**：
   - A 失败 = content.json 坏了 → 从 git / 60 份快照恢复，分钟级。
   - B 失败 = 数据库/服务挂了 → 需要 DBA 介入，小时级。
   - C 失败 = 插件漏洞被挂马 → 可能数天不被发现（安全面最大）。

### B 路线什么时候才值得换（明确的触发条件）

不是「永远不换」，而是给了三个可观测的触发点：

| 触发条件 | 说明 |
|---|---|
| 内容团队 > 5 人 | 需要审批流、角色分级、任务分配 |
| 需要多语言（≥3 语种） | 字段级 i18n 自建成本 > 引入框架成本 |
| 需要定时发布 / 版本灰度 | 需要调度器与内容版本树 |
| 页面数 > 200 | 单 JSON 全量传输变慢，需要拆分与 diff 接口 |

**当前这四条一条都不满足。** 所以结论是「不换」，而不是「自制比开源好」。

## 三、内容中台 vs 建站工具（产品定位）

| | 建站工具（Wix / 上线了） | 本系统（ZK-CMS） |
|---|---|---|
| 用户 | 不懂技术的小微企业主 | 有内容团队、有品牌规范的企业 |
| 自由度 | 拖拽布局，但结构受模板限制 | 结构由开发定，内容由运营填 |
| 差异化 | 无（大家都用同款模板） | 有（IA 与内容模型是定制的） |
| 失败模式 | 想改结构 → 换模板 → 内容重填 | 想改结构 → 找开发（但内容不丢） |

**定位一句话**：建站工具卖的是「不用开发」，我们做的是「**开发一次，之后不用开发**」。这两件事的边界很清楚：结构变更仍然需要开发，内容变更完全不需要。

## 四、不合格的竞品方案（明确排除）

| 方案 | 排除理由 |
|---|---|
| 用 Notion / 飞书文档做官网 | 无 SEO、无自定义域名体验、加载慢 |
| 用微信公众号代替官网 | 无法被搜索引擎收录；B 端客户要看官网才信任 |
| 用 GitHub Pages + 手写 Markdown | 结构不可控（15 个产品页要 15 份 md），运营不会用 git |
| 用 WordPress + 静态化插件 | 复杂度 = WordPress + 插件 + 静态化，三层失败模式 |

## 五、结论

1. **同业竞品教给我们的不是设计，是信息密度**：规格表、基地数据、客户名单必须结构化，才能被客户「自己核查」。
2. **技术选型的胜负手是约束，不是先进程度**：在「无外网 + 无专职前端 + 无数据库运维」三个约束下，自建静态管线是唯一不需要额外运维成本的解。
3. **给自己留了换路的触发条件**（见 §2 的三个条件），避免「自研到底」的路径依赖。
