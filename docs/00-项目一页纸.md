# 项目一页纸 · 中开服务官网改版（ZK-CMS）

| 项 | 内容 |
|---|---|
| 项目名 | 中开服务官网改版 · 内容中台 ZK-CMS |
| 我的角色 | 产品负责人 / 0→1 独立交付（需求、信息架构、PRD、原型、后台前后端、部署） |
| 时间 | 2026.09 立项；2026.10.15 首次提交；当前持续迭代 |
| 现状 | 已上线运行，双站 41 页，后台 35 个接口，运营部日常使用 |
| 一句话 | 把官网从「外包交付物」变成「运营自己维护的内容产品」 |

## 1. 背景（Why now）

三个变化同时发生，把原官网的脆弱性放大了：

1. **业务扩张**：产品线 5 → 15 条，交付基地 1 → 7 个。每加一条产品线，官网要新增 1 个详情页 + 改导航 + 改产品列表 + 改首页卡片 + 改相关推荐，全部依赖开发。
2. **政策窗口**：《关于促进数据标注产业高质量发展的实施意见》（2025.01，四部门）与「人工智能+」行动意见（2025.08）之后，数据标注从「劳动密集型外包」被推到「数据要素基础设施」位置，客户开始主动搜索、比对供应商——官网第一次成为获客入口，而不是电子名片。
3. **自有产能**：集团本身有内容生产团队（公众号日更、资讯周更），但内容进不了官网，因为每次改动都要排期。

**结论**：瓶颈不在设计，在内容的生产关系。

## 2. 目标（Success criteria）

不做「更好看」，做「可运营」。三层目标，逐层验收：

| 层 | 目标 | 量化口径 | 达成 |
|---|---|---|---|
| 业务目标 | 官网内容与业务同步 | 新增一条产品线从「2 周」降到「≤10 分钟」，且不需要开发介入 | ✅ 后台新增产品 → 自动进导航/产品超市/相关推荐，全链路 ≤10 分钟 |
| 用户目标 | 运营能独立改完并发布 | 一次文案修改的操作步骤 ≤ 4 步（找页 → 改 → 预览 → 发布） | ✅ 4 步；提供「保存并发布」一步到位兜底 |
| 系统目标 | 发布快且可回滚 | 全站发布 < 1 s；单页 < 0.1 s；发布失败站点零变化 | ✅ 全量 0.22 s / 单页 0.07 s / 失败自动回滚 |

## 3. 范围（Scope）

**做**：信息架构重构、内容模型（218 字段）、运营后台（编辑 / 预览 / 发布 / 回滚 / 历史 / 搜索替换 / 图库 / 账号 / 审计 / SEO / 公众号同步）、增量构建引擎、双站与产品独立站、部署链路。

**不做（并给出理由）**——这一节比「做」更重要：

| 不做 | 理由 |
|---|---|
| 引入 Strapi / Directus / WordPress | 需要 Node 运行时 + 数据库 + 常驻服务；现方案的静态产物 + 标准库后台可在 CentOS 7 / Python 3.6 / 无外网环境直接跑。**换来的能力（审批流、多语言、定时发布）当前一个都用不上。** |
| 在线富文本（WYSIWYG）编辑器 | 一期用纯 textarea 是刻意的：富文本会引入 XSS 面与 HTML 结构漂移，而当前生成器是 f-string 拼装，无法承受结构污染。二期改 Markdown（可 diff、无 XSS 面）而非 WYSIWYG。 |
| 支付通道 / 在线下单 | 需要支付资质与对账体系，合规成本高于收益；产品线客单价高，走线下商务。 |
| 移动端 App / 小程序后台 | 218 个字段的编辑需要大屏；移动端只做「查看发布状态 + 紧急下线」这一件事，不做全量编辑。 |
| 前端框架重写（Vue/React） | 现有 2416 行原生 JS 的交互逻辑是对的，缺的是组件能力。为改而改会引入构建链与依赖升级负担。 |

## 4. 结果（Results）

| 指标 | 改造前 | 改造后 | 口径 |
|---|---|---|---|
| 改一句话的周期 | 2 周（排期） | 2 分钟（含发布） | 从提需求到线上生效 |
| 全站发布 | 4.5 s（6 个子进程串行） | 0.22 s | 41 页全量，同机实测 |
| 单页发布 | 4.5 s（全量重建） | 0.07 s | 只重建 1 页 |
| 内容丢失事故 | 存在（整份覆盖无锁） | 0（rev 乐观锁 + 409） | 双人并发保存 |
| 发布失败后果 | 站点半新半旧 | 自动回滚，41 页逐字节不变 | 人为杀生成器验证 |
| 内容资产 | 散落在 HTML 里 | 218 字段 / 13 类型 / 单一真源 | content.json |

## 5. 我踩过的最大的三个坑

1. **「假回滚」**：初版发布失败时只把 HTML 拷了备份，从不恢复，但前端文案写着「已自动回滚」。运营以为安全，实际站点处于半新半旧状态。教训：**任何「已回滚」的提示，必须有一条对应的验证脚本能证明它。**
2. **增量发布的边界**：为了快，第一版只想重建「改动字段所属页面」。但 `site.phone` 出现在每一页页脚、`products[]` 影响全站导航——字段级影响面算错一次，就会出现「电话改了但页脚还是旧的」。解法是把「什么改动必须全量」写成显式规则（见 PRD §6.3），宁可多建也不能漏。
3. **把线上当预览环境**：一期没有「未发布预览」，运营只能保存 + 发布才能看到效果。这不是体验问题，是**事故源**——改错字直接上线。二期补了 `_preview/` 影子目录整站渲染。
