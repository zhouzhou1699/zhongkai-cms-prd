# 数据指标与埋点

> 一个官网上线后最常见的失败是：**没有人知道它有没有用**。本文定义北极星指标、漏斗、事件表，以及当前（诚实的）埋点现状。

## 一、北极星指标

**「有效内容更新次数 / 周」** —— 一周内运营独立完成并上线的内容改动次数。

选它的理由：
- 它直接对应立项要解决的问题（改不动 → 改得动）。
- 它不依赖流量（流量受投放影响，不能衡量产品好坏）。
- 它是先导指标：内容更新频次上来，SEO 收录与询盘才会跟着上来。

| 层级 | 指标 | 口径 | 当前值 |
|---|---|---|---|
| 北极星 | 有效内容更新次数 / 周 | 同一周内 publish 成功且 changed > 0 的次数 | 待埋点采集 |
| 一级 | 发布成功率 | publish ok=true / 总 publish 次数 | 可查 `admin/audit.log` |
| 一级 | 平均发布耗时 | publish 完成 - 开始 | 0.2–0.3 s |
| 一级 | 内容项总数 | 字段数 + 文章数 | 218 字段 + 6 篇文章 |
| 二级 | 运营自助率 | 无技术介入的发布 / 总发布 | 目标 > 90% |
| 二级 | 预览使用率 | 用过预览的发布 / 总发布 | 目标 > 50% |
| 二级 | 冲突发生率 | 409 次数 / 保存次数 | 用于判断是否要拆分编辑权限 |
| 三级 | 官网询盘数 | 留言表单提交数 | **0（表单未实现）** |
| 三级 | 产品页跳出率 | — | 未埋点 |

> 诚实说明：当前系统**没有前端埋点**（无 GA / 百度统计 / 自建事件），所以三级指标全部为「不可测」。这是路线图里的 P2 项。

## 二、转化漏斗（当前是断的）

```
① 搜索引擎 / 直链 / 公众号 →   落地页（41 页）
② 浏览产品页 / 解决方案页      ← 可测（需埋点）
③ 点击「预约咨询 / 提交需求」   ← 可测
④ 填写并提交表单              ← ❌ 断点：没有 <form>、没有接口
⑤ 销售跟进                    ← 手工（企业微信）
```

**④ 是断点。** 全站 41 个页面里只有一个 `<form>` 标签，在登录页。所有「提交需求」「预约咨询」按钮都没有绑定任何提交逻辑，但页面文案承诺「提交后 1 个工作日内与您联系」。

这不是「待优化」，这是**对访客的承诺没有兑现**。

### 修复方案（P1，1–2 天）

| 项 | 方案 |
|---|---|
| 前端 | 原生 `<form>` + `fetch` 提交，三字段必填（姓名 / 手机 / 需求描述），蜜罐字段防机器人 |
| 接口 | `POST /api/lead`：限流（同 IP 5 次/小时）、字段校验、写 `admin/leads.jsonl` |
| 后台 | 「客户线索」页：列表 / 已读 / 标记状态 / 导出 CSV |
| 通知 | 企业微信机器人 webhook 推送（无需第三方依赖） |
| 埋点 | 提交成功事件 + 来源页 UTM |

## 三、事件表（计划埋点，自建轻量方案）

不上 GA（境外脚本，国内加载不稳且合规审查麻烦）。自建 `POST /api/track`，写 JSONL，后台出报表。

| 事件 | 触发 | 参数 | 用途 |
|---|---|---|---|
| `page_view` | 页面加载 | `path, referrer, utm_*, screen` | 流量与来源 |
| `product_view` | 产品详情页加载 | `slug` | 哪些产品被看 |
| `cta_click` | 点「预约咨询 / 联系我们」 | `path, position` | 转化意图 |
| `form_start` | 表单首个输入 | `path` | 表单流失点 |
| `form_submit` | 提交成功 | `path, has_phone` | **核心转化** |
| `form_error` | 校验失败 | `field, reason` | 表单摩擦 |
| `phone_click` | 点电话 `tel:` | `path` | 移动端转化 |
| `download` | 下载资料 | `file` | 内容价值 |
| `publish` | 后台发布成功 | `mode, pages, ms` | 北极星指标 |
| `publish_fail` | 发布失败 | `page, error` | 稳定性 |
| `save_conflict` | 保存 409 | `user, changed` | 协作冲突 |
| `preview` | 点预览 | `user` | 预览使用率 |

**采集原则**：
- 首方数据（自己域名下），不外发。
- 不做跨站追踪，不存 IP 明文（存 hash 用于去重）。
- 事件量级小（日均 UV 预计 < 500），JSONL 足够，不需要数据库。

## 五、当前可用的「免费」指标（不用埋点也能算）

| 指标 | 数据源 | 命令 |
|---|---|---|
| 发布成功率 | `admin/audit.log` | `grep -c publish admin/audit.log` |
| 操作人分布 | `admin/audit.log` | 按账号计数 |
| 内容版本数 | `_build/_versions/` | `ls | wc -l`（当前 0，快照机制刚上线） |
| 备份数 | `_build/_backup_publish/` | 当前 18 份 |
| 页面体积 | 文件系统 | 平均 23 KB，最大 59 KB |
| 构建耗时 | publish 状态 | 0.2–0.3 s |

> 这些指标虽然粗糙，但足以回答「系统在被用吗」这个问题。**先有可观测性，再有精细指标。**

## 六、指标设计的三个反例（我们刻意没做的）

| 反例 | 为什么不做 |
|---|---|
| 把「页面 PV」当北极星 | PV 受投放与季节影响，运营无法通过产品能力影响它 |
| 把「字段填充率」当健康指标 | 「电话字段有值」不代表内容正确；填满 218 个字段也不代表官网有用 |
| 把「发布次数」直接当北极星 | 可以被「改一个空格发布一次」刷上去，必须加 `changed > 0` 与「内容有效变更」约束 |
