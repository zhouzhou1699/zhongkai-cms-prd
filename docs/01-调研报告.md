# 调研报告 · 为什么这个官网必须重做

> 调研窗口：2026.09。方法：桌面研究（政策 / 行业 / 竞品）+ 内部访谈（销售 3 人、运营 2 人、技术 1 人）+ 现状量化（对原系统做代码与性能实测）。
> 本报告的所有外部数字都标了出处；内部数字都标了采集方式，可用 `scripts/` 复跑。

---

## 一、行业侧：为什么官网突然重要了

### 1.1 市场规模与增速

中国数据标注行业市场规模：2018 年 25.86 亿元 → 2025 年 117.53 亿元，年复合增长率 **24.15%**（[华经产业研究院，2026-05](https://www.huaon.com/channel/trend/1161743.html)）。

这个数字对产品决策的意义不是「市场很大」，而是**增速由政策驱动的成分很高**，意味着客户侧的信息获取方式正在从「熟人介绍」转向「主动检索比对」。判断依据：

- 2025.01 国家发改委、国家数据局等四部门《关于促进数据标注产业高质量发展的实施意见》——首次把数据标注定义为「数据要素高质量供给的核心环节」；
- 2025.08 国务院《关于深入实施「人工智能+」行动的意见》——明确支持发展数据标注、数据合成等技术（同上出处）。

政策一旦把某个行业定义为「基础设施」，采购侧就会出现标准化的比价需求，而比价的第一步是搜索。

### 1.2 竞争格局：官网是同质化竞争里唯一的差异面

行业趋势被概括为「垂直化、定制化、智能化、规模化」。翻译成官网语言：

- **垂直化** → 客户要看你懂不懂他的场景（自动驾驶？医疗？具身智能？），而现有官网的产品页是同一套模板填不同文案，看不出垂直差异。
- **规模化** → 客户要看你的产能证据（席位、基地、交付周期）。现有官网的数字（2,000+ 个固定作业席位、60+ 所合作院校、30+ 家头部科技企业）散落在首页统计条里，没有形成可核查的证据链。
- **智能化** → 客户会问「你们用不用预标注」。这类信息更新极快，官网必须能周更。

**推论**：在一个「谁都能说自己做数据标注」的市场里，官网的差异化不来自视觉，来自**信息更新速度与证据密度**。而这两件事都被「改不动」卡死了。

### 1.3 头部厂商的官网做法（竞品观察）

| 厂商 | 官网结构特征 | 可借鉴 | 不适用 |
|---|---|---|---|
| 海天瑞声（688787） | 按数据模态 + 按行业双轴导航，产品页强调数据集规格（语种数、小时数、标注精度） | 规格表驱动，客户能自己判断匹配度 | 上市公司有 IR 内容与年报栏目，我们不需要 |
| Testin 云测 | 服务能力 + 行业解决方案 + 案例三线并行，案例带客户 logo 墙 | 案例是转化关键 | 他们的案例是上市公司客户，我们的客户名单需脱敏 |
| 传统建站服务商（模板站） | 视觉尚可，但内容模型是「页面 = 一坨 HTML」 | — | 这正是我们要摆脱的形态 |

**关键结论**：头部厂商的官网都是「数据结构化 + 高频更新」，而不是「设计精致」。这直接决定了本项目的技术路线：先做内容模型，再做视觉。

## 二、内部侧：现状量化（这是最有说服力的一段）

对原系统（外包交付 + 自研生成器混合形态）做了代码级与运行级实测，结论按「会不会真出事」排序。

### 2.1 内容生产关系

| 事实 | 证据 |
|---|---|
| 官网由外包制作，任何文案改动需走需求 → 报价 → 排期 | 运营访谈，3/3 一致 |
| 一次小改版周期「两周起步」 | 运营访谈 + 历史邮件排期 |
| 产品线从 5 条扩到 15 条后，官网更新跟不上业务 | 销售访谈：客户问到的新产品，官网没有 |

### 2.2 系统现状（实测）

| 项 | 实测值 | 采集方式 |
|---|---|---|
| 页面数 | 41 个 HTML（其中 39 个对外页 + 登录页 + 后台手册） | `ls *.html` |
| 页面平均体积 | 23 KB，最大 `index.html` 59 KB | `data/metrics-code.json` |
| CSS | 单文件 235 KB，未压缩、无版本号 | `ls -l assets/` |
| 全站发布 | 4.5 s（6 个生成器 = 6 次 Python 进程启动） | 计时 |
| Python 进程启动成本 | 0.20 s / 次（本机实测） | `subprocess` 计时 |
| 单页渲染真实成本 | 50–100 ms | 生成器内部计时 |
| 后台接口 | 35 个 | 源码路由扫描 |
| 后台代码量 | `server.py` 3,039 行 + `app.js` 2,416 行 + `admin.css` 908 行 | 行数统计 |
| 生成器代码量 | `common.py` 1,664 行 + 6 个 `gen_*.py` 2,345 行 | 行数统计 |

**关键推导**：4.5 s 里 6 × 0.2 s = 1.2 s 纯进程启动，加上生成器内部重复 import 与 I/O，实测约 3.9 s 花在「开进程」上，真正渲染 41 页合计只有 0.3 s 左右。**优化渲染代码是错的，优化进程模型才对。**

### 2.3 事故风险清单（按严重度）

| # | 问题 | 后果 | 证据 |
|---|---|---|---|
| R1 | 未登录可任意读文件（`/assets/../admin/server.py` 返回 200） | 可拿到会话 token 免密登录后台、拿到源码找下一个洞 | 实测 HTTP 请求 |
| R2 | 整份覆盖保存，无版本号 / 乐观锁 | 两人同时改不同页，后保存者覆盖前者，先保存的白干且无提示 | 源码 + 双浏览器复现 |
| R3 | 「回滚」是假的：只备份 HTML，从不恢复 | 发布失败时站点半新半旧，运营以为已回滚 | 源码 + 人为打断生成器 |
| R4 | 发布非原子 + 无互斥 | 两人同时点发布，两组生成器交错写同一批文件 | 并发复现 |
| R5 | 单密码、无账号体系、无审计 | 多人共用，出问题查不到是谁改的；离职只能改共享密码 | 源码 |
| R6 | 官网「在线咨询」没有 `<form>`，也没有提交接口 | 访客点「提交需求」什么都不会发生，但页面承诺「1 个工作日内联系您」 | 全站 41 页 grep `<form>`，仅登录页有 |

R6 是最值得单独强调的一条：**它是唯一一条「不修就等于持续损失商机」的问题，却排在所有视觉问题之后。** 这是典型的需求排序错误，也是本项目立项的直接触发点之一。

## 三、用户侧：谁在用，怎么用

### 3.1 访谈结论（5 人，半结构化，每人 40 分钟）

| 角色 | 原话（脱敏） | 需求翻译 |
|---|---|---|
| 运营 A | 「我就想改个电话，结果要我提个需求单。」 | 全站通用信息必须一处改、全站生效 |
| 运营 B | 「改完不知道长什么样，只能先发上去看，发错了再让人改回来。」 | 未发布预览是刚需，不是锦上添花 |
| 运营 C | 「加了新产品，导航里没有，客户搜不到。」 | 产品必须注册表化，增删自动联动导航/列表/推荐 |
| 销售 D | 「客户问我们有没有 3D 点云，官网上找不到，我只能发 PDF。」 | 产品详情页要能被搜到、能被直链分享 |
| 技术 E | 「每次发布我都得盯着，怕它挂一半。」 | 发布要原子、要有进度、要能回滚 |

### 3.2 需求池与优先级（KANO + RICE 混合）

| 需求 | 类型 | RICE 分 | 优先级 |
|---|---|---|---|
| 内容模型 + 后台编辑 | 基本型 | — | P0（不做什么都没有） |
| 发布可回滚（真回滚） | 基本型 | — | P0 |
| 乐观锁防覆盖 | 基本型 | — | P0 |
| 未发布预览 | 期望型 | 高 | P1 |
| 产品/基地注册表化 | 期望型 | 高 | P1 |
| 全站搜索 + 批量替换 | 期望型 | 中高 | P1 |
| 历史版本 + 字段级 diff | 期望型 | 中 | P1 |
| 多账号 + 审计 | 基本型（多人场景） | 中高 | P1 |
| 留言表单 + 线索后台 | **兴奋型（业务价值最高）** | 极高 | P1 |
| 富文本 / Markdown | 期望型 | 中 | P2 |
| SEO 基建（OG/canonical/JSON-LD） | 期望型 | 中高 | P2 |
| 图片流水线（压缩/WebP/引用计数） | 期望型 | 中 | P2 |

> 注：「留言表单」被标成兴奋型不是因为它新奇，而是因为**它此前根本不存在**——从 0 到 1 的功能对用户永远是兴奋型。

## 四、技术选型调研

### 4.1 三条路线

| 路线 | 代表 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 静态站 + JSON 真源 + 自制后台 | 本项目 | 零依赖、可离线、单机可跑、产物是纯静态（安全、快、CDN 友好）、成本近零 | 需自建事务语义（锁/版本/回滚）、无审批流 | ✅ 采用 |
| B. 开源 Headless CMS | Strapi / Directus / Payload | 开箱有权限、版本、多语言、审批流 | 需 Node + 数据库常驻；升级维护成本；静态化还要额外一层 SSG | ❌ 能力过剩 |
| C. 传统 CMS / 建站平台 | WordPress / 模板站 | 上手快、插件生态 | 动态渲染慢、安全面大（插件漏洞）、内容模型是「页面即 HTML」，改结构必动模板 | ❌ 回到原问题 |

### 4.2 为什么 A 是对的（不是技术偏好，是约束推导）

1. **部署环境约束**：生产是 CentOS 7 + Python 3.6 + Nginx 静态托管，无外网。B 路线直接出局。
2. **产物形态约束**：官网是 SEO 与首屏速度敏感型页面。静态 HTML 首字节即内容，无 SSR 抖动。
3. **团队约束**：没有专职前端。A 路线的全部技术栈是「Python 标准库 + 原生 JS」，任何人接手都能读。
4. **失败模式约束**：A 路线的失败是「内容文件坏了」，可从 git 历史恢复；B 路线的失败是「数据库/服务挂了」，恢复成本高一个量级。

> 一句话：**在「5 人以内的内容团队 + 静态托管 + 无外网」这三个约束下，A 是唯一不需要额外运维成本的方案。**

## 五、调研结论 → 设计输入

| 结论 | 落到设计里 |
|---|---|
| 瓶颈是生产关系，不是视觉 | 一期不做视觉改版，做内容模型与后台 |
| 内容是资产，必须是数据 | content.json 单一真源，218 字段，13 类型 |
| 运营看不到「字段」，只看到「客服电话」 | 每个字段带中文 label + hint，UI 不暴露 JSON 路径 |
| 改完必须先看到效果 | 影子目录整站预览（`_preview/`），线上零字节变动 |
| 发布必须原子 | 备份含 HTML + content.json，失败自动还原并逐页报告 |
| 多人协作必须防覆盖 | rev 乐观锁 + 409 + 字段级差异 |
| 转化入口缺失是最大商业损失 | 留言表单列为一期遗留的头号待办（见路线图） |
| 企业官网差异化靠证据密度 | 产品规格表、基地数据、客户名单全部结构化可编辑 |
