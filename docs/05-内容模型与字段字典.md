# 内容模型与字段字典

> 这是整个项目里最「产品经理」的一份文档：把 41 个页面拆成 218 个可编辑字段，让运营看到「客服电话」而不是 `site.phone`。
> 完整字典（218 行）见 [data/fields.json](../data/fields.json)，本文讲方法与关键结构。

## 一、建模方法：从「页面」到「字段」的四步

### 第 1 步：找重复（去重）

41 个页面里，同一段内容重复出现的比例极高：

| 内容 | 出现次数 | 处理 |
|---|---|---|
| 客服电话 / 邮箱 / 地址 / 备案号 | 41 页页脚 + 2 个联系页 | 提到 `site.*`，全站引用 |
| 11 个产品的能力卡说明 | 15 个产品页各 4 张 | 按产品分，但**共用模板**（同一套 5 字段结构） |
| 7 个基地的名称 / 省份 | 基地页 + 基地列表 + 集团站导航下拉 | 提为 `bases.<slug>.{name, alias, prov}`，被多处引用 |
| 页脚的「关于中开服务」「关于中开集团」 | 各 1 段，出现在所有页 | 提到 `site.footer_about_*` |

**量化结果**：218 个字段覆盖了原本 41 页里约 600 处文案节点——去重率约 64%。这直接决定了「改一次电话全站生效」能不能做到。

### 第 2 步：分类型（决定控件）

把每个字段按「编辑动作」归到 13 种类型里（详见 PRD §4.2）。判断标准只有一个：**运营要做的是「打字」「加一条」「换张图」还是「改个数字」**。

最容易分错的是 `paras`（段落数组）与 `longtext`（长文本）：

| | `longtext` | `paras` |
|---|---|---|
| 用于 | 一段连续的话 | 多条独立短句（每行一条，可能对应一张卡） |
| 例子 | 产品简介、详细介绍 | 能力卡说明 ×4、规格参数值 ×6 |
| 编辑体验 | 一个大文本框 | 带序号的可增删行，可上下移动 |
| 分错后果 | 运营被迫在文本框里手动分行，生成器按位置切分，一改全错位 | 一句话被拆成 4 行，排版散架 |

### 第 3 步：定层级（三层收敛）

```
站点 → 页面分组 → 页面 → 字段
```

关键指标不是「总字段数」，而是**单页字段数**。实测分布：

| 单页字段数 | 页面 | 评价 |
|---|---|---|
| 1–3 | 12 个能力页 | 一屏搞定 |
| 5 | 15 个产品页 | 一屏搞定 |
| 7 | 基地列表页 | 一屏偏长 |
| 10–11 | 2 个首页 + 7 个基地页 | 需要滚动，可接受 |

**没有一页超过 11 个字段。** 这是刻意的约束：超过 12 个字段，运营就开始「找不到刚才改的那个框」。

### 第 4 步：加元数据（label / hint / names）

每个字段节点长这样：

```json
"phone": {
  "v": "182-6337-1901",
  "label": "客服电话",
  "type": "text"
}
```

带行标题的数组字段多两个键：

```json
"feats": {
  "v": ["支持文本、图像、视频…", "内置 AI 预标注…", "…", "…"],
  "label": "核心能力 · 卡片说明",
  "type": "paras",
  "hint": "按顺序对应 4 张能力卡；卡片标题与说明均可编辑",
  "names": ["多模态标注", "标注效率", "质检体系", "数据交付"],
  "edit_names": true
}
```

- `label` 是给运营看的中文名（必填）。
- `hint` 解释「这个字段在页面上长什么样、要几条」（强烈建议给数组类字段写）。
- `names` 是行标题（能力卡标题、规格行参数名），与 `v` 是两条等长平行数组。
- `edit_names` 控制行标题是否可改（有些行标题是刻意的设计语言，不允许改）。

## 二、13 种字段类型速查

| 类型 | 数量 | 典型字段 | 控件要点 |
|---|---|---|---|
| `paras` | 71 | 正文段落、能力卡说明、规格值、相关推荐简介 | 可增删 + 上下移 + 序号 |
| `longtext` | 57 | 简介、详细介绍、页脚文案 | 多行域，字数提示 |

## 三、关键结构详解

### 3.1 全站通用（`site`，11 字段）

| 字段 | label | 类型 | 出现在 |
|---|---|---|---|
| `phone` | 客服电话 | text | 41 页页脚 + 2 联系页 |
| `email` | 企业邮箱 | text | 同上 |
| `address` | 详细地址 | text | 同上 |
| `icp` | ICP 备案号 | text | 页脚（合规必需） |
| `worktime` | 工作时间 | text | 联系页 |
| `footer_about_service` | 页脚 · 关于中开服务 | longtext | 服务站 23 页 |
| `footer_about_group` | 页脚 · 关于中开集团 | longtext | 集团站 15 页 |
| … | | | |

**为什么这 11 个要单独提**：它们**出现在每一页**，所以任何改动都会触发全量重建（41 页）。这不是性能缺陷，是正确性要求。

### 3.2 产品注册表（`products[]`，15 项）

```json
{
  "slug": "product-annotation",
  "name": "大模型通用数据标注平台",
  "sub": "多模态标注",
  "sub_en": "Large Model Annotation Platform",
  "kind": "sw",
  "banner": "面向大模型训练的数据标注全流程平台，覆盖采集、清洗、标注、审核与交付。",
  "deg": 160,
  "feats_names": ["多模态标注", "标注效率", "质检体系", "数据交付"],
  "specs_names": ["产品定位", "支持模态", "部署方式", "适用规模", "核心功能", "交付标准"],
  "related": [
    {"name": "3D点云标注平台", "href": "product-3d.html"},
    …
  ]
}
```

| 键 | 作用 | 谁读它 |
|---|---|---|
| `slug` | 文件名 / 独立站目录名 / 锚点 | 生成器、独立站、导航补丁 |
| `name` / `sub` / `sub_en` | 卡片标题 / 中文角标 / 英文角标 | 产品超市、导航下拉、相关推荐 |
| `kind` | `sw` 软件 / `hw` 硬件 | 产品超市分区 |
| `banner` | 一句话定位 | 产品超市卡片、详情页头 |
| `deg` | 无头图时的渐变角度 | 详情页视觉 |
| `feats_names` / `specs_names` | 能力卡与规格行的**列标题** | 详情页模板（值在 `pages.<slug>` 里） |

**核心洞察**：产品的「结构」（几行规格、几列能力）在注册表里，「内容」（每行写什么）在 `pages.<slug>` 里。所以新增一个产品 = 注册表加一项 + `pages` 加 5 个字段，模板零改动。

**已知技术债（U13）**：`feats_names` 与 `pages.<slug>.feats.v` 是平行数组，靠位置对齐。任何一方错位，整列内容串行。下一轮应改成对象数组 `[{name, desc}]`。

### 3.3 基地注册表（`bases{}`，7 项 × 11 字段）

```
name(基地名称) alias(别名) prov(所在省) deg(头图色调角度) tags(标签)
desc(一句话简介) detail(详细介绍) image(头图)
nums(数据指标 stats) caps(核心职能卡 cells) biz(入驻与业务方向 paras)
```

`name / alias / prov` 三个字段是「导航敏感字段」——它们出现在集团站每一页的导航下拉里，改动会触发跨页重建。这条规则如果写错，就会出现「基地改名了但导航还是旧名」的事故。

### 3.4 资讯模型（`news_page.cats[]`）

```json
{
  "id": "science",
  "name": "科普知识",
  "desc": "数据标注、AI 基础知识科普",
  "items": [
    {
      "date": "2026-04-15",
      "title": "什么是数据标注？一文读懂人工智能背后的"数据燃料"",
      "image": "assets/uploads/news-science-1.jpg",
      "slug": "what-is-data-annotation",
      "author": "中开集团",
      "body": [
        {"type": "p", "text": "…"},
        {"type": "h", "text": "数据标注到底在做什么"},
        {"type": "img", "src": "…"}
      ]
    }
  ]
}
```

正文用**块数组**而不是 HTML 字符串——这是全项目唯一一处「结构化富文本」，因为资讯是唯一需要小标题与配图的场景。它也是二期把长文全部改成块数组/ Markdown 的样板。

### 3.5 首页（`home_service` / `home_group`，各 10–11 字段）

| 字段 | 类型 | 页面位置 |
|---|---|---|
| `hero_title` / `hero_desc` | text / longtext | 首屏 |
| `intro_image` / `intro_badge` / `intro_h3` / `intro_paras` / `intro_cells` | image / text / text / paras / cells | 「走进我们」 |
| `stats` | stats | 数据条（5 省 / 1,929 席位 / 58 院校 / 29 企业） |
| `philosophy_tabs` | tabs | 企业理念 |
| `milestones` | milestones | 发展历程 |
| `news`（仅集团站） | news | 资讯区 |

## 五、这套模型的问题（诚实记录）

| # | 问题 | 影响 | 计划 |
|---|---|---|---|
| M1 | 字段元数据（label/type/hint）混在数据里 | 数据文件是「数据 + schema」混合体，任何非后台消费者都要跳过元数据 | 抽出 `schema.json`，content.json 只留值 |
| M2 | 「这个页面有哪些字段」写在 `app.js` 的 `PAGE_FIELDS` 里 | 改一个字段要动 3 处（content / app.js / 生成器） | 同上，schema 单一真源 |
| M3 | 平行数组（`feats` + `feats_names`） | 位置错位导致内容串行，且无校验 | 改对象数组 |
| M4 | `version: 1` 字段无人读取 | 有版本号但没有迁移机制，是假的安全感 | 要么实现迁移，要么删掉 |
| M5 | 无字段级校验规则 | 运营能把 4 条能力卡写成 3 条，页面按位置取第 4 条时取到 undefined | schema 里加 `min/max/required` |
